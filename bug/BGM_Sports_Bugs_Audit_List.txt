BUG-003: [Registration / Login] Click Password Visibility Toggle Displays Inverted Behavior
--------------------------------------------------------------------------------
- Severity    : Medium
- Status      : OPEN (Pending Theme Update)
- Affected    : main/platform/core/base/resources/views/forms/fields/password.blade.php
                main/platform/core/base/resources/views/forms/fields/password-toggle-script.blade.php
- Description : When entering a password, the show/hide password toggle (eye icon) behaves
                counter-intuitively. The initial state shows a slashed/closed eye (ti ti-eye-off)
                while the text is masked. When clicked to reveal, it shows an open eye (ti ti-eye).
                Users expect the button icon to indicate the action to be performed (e.g., an open
                eye icon invites the user to "view" the hidden password, or vice-versa).
- Steps to Reproduce:
  1. Navigate to http://localhost/vichu/bgm/register or /login.
  2. Focus on the Password input field and type a password.
  3. Observe initial icon state and click the toggle button.
- Expected    : The toggle state should follow standard UI convention:
                - When password is hidden (••••••••): icon displays an open eye (Action: "Show password").
                - When password is plain text: icon displays a slashed eye (Action: "Hide password").
- Actual      : Slashed eye is shown when hidden; clicking reveals text with open eye, causing confusion.
- Technical Fix Recommendation:
  In `password.blade.php`, change initial icon to `ti ti-eye`.
  In `password-toggle-script.blade.php`, invert the icon swap logic:
  ```javascript
  if (passwordField.getAttribute('type') === 'password') {
      passwordField.setAttribute('type', 'text');
      this.innerHTML = `{!! BaseHelper::renderIcon('ti ti-eye-off') !!}`;
  } else {
      passwordField.setAttribute('type', 'password');
      this.innerHTML = `{!! BaseHelper::renderIcon('ti ti-eye') !!}`;
  }
  ```

BUG-017: [Forgot Password] Registered Email Rejection ("This email ID is not in our records")
--------------------------------------------------------------------------------
- Severity    : High
- Status      : OPEN (Pending Investigation)
- Affected    : main/platform/plugins/ecommerce/src/Http/Controllers/Customers/ForgotPasswordController.php
                main/platform/core/acl/src/Traits/SendsPasswordResetEmails.php
                main/platform/plugins/ecommerce/src/Models/Customer.php
- Description : When a user registers, receives the registration confirmation, and later requests a
                password reset via Forgot Password, the form returns "This email ID is not in our records".
- Root Cause Analysis:
  1. Case Sensitivity & Whitespace: Registration stores emails without `strtolower(trim($email))`. If
     user registers with capital letters or trailing spaces, exact DB match on password reset fails.
  2. Unconfirmed Account Exclusion: If email verification is enabled, `Password::broker('customers')`
     or customer repository might ignore accounts where `confirmed_at` is null.
  3. Pre-fix Typos: Users registered before BUG-007 fix had invalid addresses stored, making recovery
     impossible.
- Steps to Reproduce:
  1. Register a new user with email "User.Test@domain.com".
  2. Navigate to Forgot Password page.
  3. Enter "user.test@domain.com" and submit.
- Expected    : Email is normalized, user is found, and password reset email is queued.
- Actual      : System displays "This email ID is not in our records".
- Technical Fix Recommendation:
  In `SendsPasswordResetEmails::validateEmail` and `credentials()`, apply:
  ```php
  protected function credentials(Request $request)
  {
      return ['email' => strtolower(trim($request->input('email')))];
  }
  ```
  Ensure `Customer` registration mutator also forces `strtolower(trim($value))`.

BUG-001: [Cart] Header Badge Count Increments with Quantity Instead of Distinct Items
--------------------------------------------------------------------------------
- Severity    : High
- Status      : OPEN
- Affected    : main/platform/plugins/ecommerce/src/Cart/Cart.php
                main/platform/plugins/ecommerce/src/Http/Controllers/Fronts/PublicCartController.php
                main/platform/themes/shofy/partials/header/actions.blade.php
                main/platform/plugins/ecommerce/public/js/front-ecommerce.js
- Description : When a customer adds 1 product with quantity 3, the header cart badge counter displays
                "3" instead of "1". Most modern e-commerce standards require the badge counter to reflect
                the number of distinct items (line items) in the cart.
- Technical Findings:
  - In `Cart.php`: `count()` returns `$content->sum('qty')` (total item units), while `countProducts()`
    returns `$this->getContent()->count()` (distinct product lines).
  - In `actions.blade.php`, `Cart::instance('cart')->countProducts()` is rendered on page load, but when
    items are added via AJAX, `getDataForResponse()` or client JS may replace it with total quantity or
    vice versa.
- Steps to Reproduce:
  1. Add 1 Cricket Bat to cart. Badge shows "1".
  2. Increase quantity of the bat to 5 in mini-cart or cart page.
  3. Observe header badge count.
- Expected    : Cart badge remains "1" (1 distinct product type in cart).
- Actual      : Cart badge updates to "5".
- Technical Fix Recommendation:
  Verify whether the business requirement strictly mandates distinct product count or total quantity.
  If distinct count:
  Ensure `PublicCartController::getDataForResponse` sends `'count' => $cartInstance->countProducts()`,
  and all theme header badges bind consistently to `countProducts()`.

- Technical Fix Recommendation:
  In theme SASS / CSS, ensure `.tp-product-action-btn-2.active svg, .tp-product-action-btn.active svg`
  forces `fill: var(--tp-theme-primary) !important; color: var(--tp-theme-primary) !important;`.

BUG-016: [Registration] Switching "I am a vendor" to "I am a customer" Submits Hidden Vendor Fields
--------------------------------------------------------------------------------
- Severity    : High
- Status      : OPEN (Needs Verification & Backend Safeguard)
- Affected    : main/platform/plugins/marketplace/resources/js/customer-register.js
                main/platform/plugins/marketplace/src/Http/Requests/RegisterRequest.php
- Description : A user begins filling out vendor fields ("Shop Name", "Shop URL"), but changes their
                mind and selects "I am a customer". The vendor fields slide up (hidden), but the input
                values remain populated and may be sent in the POST payload.
- Root Cause Analysis:
  In `customer-register.js`:
  ```javascript
  function syncVendorFields(form) {
      var checked = form.find('input[name="is_vendor"]:checked').val();
      var wrapper = form.find('[data-bb-toggle="vendor-info"]');
      if (checked == 1) {
          wrapper.find(vendorFields).prop('disabled', false);
      } else {
          wrapper.find(vendorFields).val('').prop('disabled', true);
      }
  }
  ```
  While `customer-register.js` attempted to disable the fields, if the user toggles via standard
  radio click before the script initializes, or if the form is submitted via enter key, backend
  request receives `is_vendor = 0` but creates orphaned store records or fails with validation errors.
- Technical Fix Recommendation:
  In backend `RegisterController` or `RegisterRequest`:
  If `$request->input('is_vendor') != 1`, explicitly purge all vendor-related keys (`shop_name`,
  `shop_url`, `shop_phone`) from `$request` before processing.

BUG-018: [Product Listing - Cricket] Price Range Filter Slider Max (1,500) Cuts Off Products Up to ~1,800
--------------------------------------------------------------------------------
- Severity    : High
- Status      : OPEN
- Affected    : main/platform/plugins/ecommerce/src/Supports/EcommerceHelper.php (Line 1423)
                main/platform/plugins/ecommerce/resources/views/themes/includes/filters/price.blade.php
- Description : On the Cricket category page, the sidebar price range slider caps out at 1,500.
                However, cricket equipment in this category includes items priced up to ~1,800.
                Consequently, users cannot filter or view products priced between 1,500 and 1,800.
- Root Cause Analysis:
  1. Setting Override: In `EcommerceHelper::getProductMaxPrice()`, if the admin setting
     `max_product_price_for_filter` is defined in Admin Panel > Ecommerce > Settings, it returns
     that hardcoded integer (e.g. 1500) rather than dynamic database max price.
  2. Cache Stale: `Cache::remember('ecommerce_product_price_range_...', Carbon::now()->addHour())`
     caches the max price for 1 hour. If higher-priced products were added recently, the cache
     remains at the old price.
  3. Variation Price Exclusion: `Product::query()->max('price')` checks only the parent product's
     `price` column. If variations (sizes, willow grades) have prices up to 1,800 while the parent
     product base price is 1,500, the slider maximum ignores variation prices!
- Steps to Reproduce:
  1. Open http://localhost/vichu/bgm/product-categories/cricket.
  2. Observe the price slider max value. It displays 1,500.
  3. Notice products listed with prices such as 1,750 or 1,800.
- Expected    : Price slider max dynamically scales to the highest priced item (e.g., 2,000).
- Actual      : Slider is capped at 1,500, cutting off premium products.
- Technical Fix Recommendation:
  In `EcommerceHelper.php::getProductMaxPrice()`:
  - Ensure query checks both `ec_products.price` and variation prices if variations exist.
  - Round up to the next ceiling hundreds (e.g., `ceil($maxPrice / 100) * 100`).
  - Clear the price range cache when products are created/updated in `ProductObserver`.

BUG-005: [Email Notifications] System-Generated Emails Delivered to Spam / Junk Folder
--------------------------------------------------------------------------------
- Severity    : High
- Status      : OPEN
- Affected    : `.env` (MAIL_* Configuration), DNS Records (SPF, DKIM, DMARC)
- Description : Account verification, welcome, and order confirmation emails are routed to the
                recipient's Spam/Junk folder instead of Primary Inbox across Gmail and Outlook.
- Root Cause Analysis:
  1. Local environment uses unauthenticated `mail` or `sendmail` driver without TLS authentication.
  2. The `MAIL_FROM_ADDRESS` does not match the server's sending domain.
  3. The sending domain lacks valid SPF (`v=spf1 include:... ~all`), DKIM, and DMARC DNS records.
- Technical Fix Recommendation:
  - Configure production SMTP service (Amazon SES, SendGrid, Mailgun, or Postmark) in `.env`:
    `MAIL_MAILER=smtp`
    `MAIL_HOST=smtp.mailgun.org`
    `MAIL_PORT=587`
    `MAIL_ENCRYPTION=tls`
  - Ensure sender domain has SPF and DKIM public keys configured in DNS.
